\begin{abstract}
Automatic generation of executable code from scientific papers is crucial
for both research aim and the practical adoption of
new methods in industry. Existing paper-to-code agents can produce
repositories that appear faithful and may score highly under
LLM-as-a-judge evaluation, but such apparent quality does not
ensure runnability or scientific reproducibility. We propose a
rubric- and execution-guided paper-to-code framework that
verifies generated repositories through intermediate-value
tests, runtime checks, and benchmark-level reproduction
criteria. Our workflow parses papers into structured JSON,
generates initial repositories through a planning-analysis-coding
pipeline, constructs paper-specific rubrics and \texttt{pytest}
tests, extracts runtime requirements, and packages the resulting
task into a Harbor-style evaluation environment. On 22
PaperBench papers, our prototype substantially improves
runnability and reveals a large gap between executable
repositories and scientifically reproducible repositories. These
results suggest that paper-to-code evaluation should move beyond
LLM-as-a-judge scores toward execution-grounded verification of
algorithmic and experimental fidelity.
\end{abstract}

\section{Introduction}

Reproducibility is essential for scientific progress, allowing
researchers to verify findings, build on previous work, and push the
boundaries of knowledge \citep{collaboration2015estimating, baker20161,
pineau2021improving}. In machine learning, however, reproducing
experimental results from a paper alone remains a persistent challenge:
documentation is often incomplete, hyperparameters are under-specified,
and a substantial fraction of accepted papers release no accompanying
code \citep{seo2025papercoder}. This forces researchers to invest
considerable effort reverse-engineering methods from prose, slowing
the pace of scientific dissemination.

Recent Large Language Models (LLMs) have shown strong capabilities in
both understanding scientific text and generating code
\citep{dubey2024llama, openai2024gpt4, reid2024gemini}, prompting a
wave of paper-to-code agents that aim to translate a research paper
directly into an executable repository \citep{seo2025papercoder,
starace2025paperbench, siegel2024corebench}. Systems such as
PaperCoder \citep{seo2025papercoder} decompose this task into
planning, analysis, and coding stages, and emit repositories that are
structurally complete and stylistically convincing. Under
LLM-as-a-judge evaluation, such repositories routinely receive high
faithfulness scores. The implicit conclusion is that the generated
code is a reasonable proxy for the paper's implementation.

We argue that this conclusion conflates three increasingly strict
properties that should be kept distinct: whether a repository
\emph{looks} faithful to the paper, whether it actually \emph{runs},
and whether it \emph{reproduces} the paper's experimental behavior. A
simple analogy is egg fried rice. A finished plate may look right,
but a positive visual judgment does not entail that the cook
understood the recipe, followed the correct procedure, or produced a
dish with the expected taste. A judge that only inspects the plate
cannot detect a missing ingredient, an inverted step, or a heat
profile that differs from the original. The same holds for
paper-to-code systems: a repository may use the wrong loss term, omit
a key normalization, depend on an uninstalled package, or execute
successfully yet fail to match the reported baseline. Existing
benchmarks largely measure surface-level repository quality and do
not separate these three properties, leaving open the question of
whether current paper-to-code agents are reproducing science or
merely producing code that resembles it.

To address this gap, we propose that paper-to-code evaluation should
be \emph{execution-grounded} rather than \emph{appearance-based}, and
we present a prototype framework that realizes this principle .
Given a paper, the framework runs three parallel agents: a
\textbf{coding agent} that emits an initial repository; a
\textbf{rubric and unit-test generation agent} that converts paper
claims into \texttt{pytest} cases targeting intermediate quantities
and final outputs; and a \textbf{runtime-information extraction
agent} that records hardware, package, dataset, and hyperparameter
requirements. A subsequent code-running and amelioration stage uses
rubric checks, test outcomes, and execution traces to revise the
repository. The final artifact is packaged as a TerminalBench-style
\citep{tbench2025} reproducibility task that can be replayed by
external agents. The novelty here is not the multi-agent
decomposition itself, but the shift in what counts as evidence of
reproduction: rather than asking only whether the final result
\emph{looks} right, the framework verifies that the repository
computes the correct intermediate quantities, runs to completion,
and satisfies benchmark-level criteria.

We organize our investigation around three research questions:
\begin{description}[leftmargin=1em,itemsep=0pt,topsep=2pt]
  \item[\textbf{RQ1}] Does LLM-as-a-judge repository quality reflect
    actual runnability and scientific reproducibility?
  \item[\textbf{RQ2}] Can paper-specific rubrics and intermediate-value
    tests better identify algorithmic implementation errors than
    end-to-end output checks?
  \item[\textbf{RQ3}] Can static and runtime feedback meaningfully
    improve generated paper-to-code repositories?
\end{description}

\noindent We make three contributions. \emph{First}, we identify and
characterize a gap between apparent repository quality, executability,
and scientific reproducibility in current paper-to-code agents.
\emph{Second}, we propose a rubric- and execution-guided workflow that
decomposes paper-to-code reproduction into paper understanding, code
generation, rubric and unit-test generation, runtime-information
extraction, static amelioration, and TerminalBench-style task
packaging. \emph{Third}, we evaluate the prototype on 22 papers from
PaperBench \citep{starace2025paperbench} and show that making
generated repositories runnable is substantially easier than
reproducing paper-level experimental claims, underscoring the need
for intermediate-value verification and stronger runtime-guided
refinement.

\section{Related Work}

\paragraph{Paper-to-code generation.} PaperCoder
\citep{seo2025papercoder} is the closest baseline to our work.
It decomposes paper-to-code into planning, analysis, and coding
stages and shows that structured repository generation
improves implementation quality over single-prompt baselines.
However, PaperCoder's main evaluation centers on repository-level
faithfulness as judged by an LLM, with comparatively limited
analysis of executability or experimental reproduction. Our
framework adopts the planning-analysis-coding skeleton but
extends it with paper-specific rubric generation, unit-test
generation, runtime-information extraction, and a code-running
amelioration loop intended to verify the generated repository
against execution-grounded criteria.

\paragraph{Reproduction benchmarks.} A growing body of work
benchmarks paper-to-code systems and code-using agents.
PaperBench \citep{starace2025paperbench} measures whether agents
can reproduce machine-learning papers from scratch using
hierarchical rubrics, and provides the papers we use in our
evaluation. SciReplicate-Bench
\citep{scireplicate2024} focuses on reproducing
algorithmic procedures from method sections.
CORE-Bench \citep{corebench2024} evaluates the reproducibility
of computational research more broadly, while REPRO-Bench
\citep{hu2025reprobench} targets end-to-end reproduction with
explicit execution checks. Compared to these benchmarks, our
focus is not on building a static benchmark but on a
\emph{generative} workflow that turns a paper into a reproducible
task on the fly, while inheriting their key insight that
execution must be part of evaluation.

\paragraph{Agentic terminal benchmarks.} Terminal-Bench
\citep{tbench2025} evaluates agents on realistic terminal tasks
using containerized environments, natural-language instructions,
test suites, oracle solutions, and time limits. Our Harbor-style
packaging adapts this evaluation philosophy to paper-to-code
reproduction: the final artifact is not a static repository but a
self-contained task that bundles paper, code, runtime
specification, and tests.

\paragraph{Test-time refinement.} Iterative self-debugging
\citep{chen2023selfdebug,zhong2024debugbench} and best-of-$N$
sampling approaches \citep{brown2024largelanguagemonkeys} have
shown that test-time feedback can improve LLM code generation.
Our amelioration loop is in this lineage, but uses
\emph{paper-specific} rubrics and intermediate-value tests as the
feedback signal, rather than generic correctness oracles or
arbitrary unit tests.

In this section we describe our framework as a \emph{stage-wise codebase transformation}. Rather than producing the final reproduction in one shot, the pipeline takes a paper $R$ and walks the repository through a sequence of states $R_0 \rightarrow R_1 \rightarrow \cdots \rightarrow R_n$, where each stage either \emph{mutates the repository} or \emph{emits a side artifact} that conditions later mutations. This view makes the framework easier to reason about and to debug: it tells us which stage \emph{creates structure}, which stage \emph{fills in behavior}, and which stage merely \emph{packages} the result. The overall pipeline is shown in Figure~\ref{fig:workflow}.

\label{sec:method-stages}
The pipeline yields four artifacts: the generated code repository $C$, the paper-specific rubric together with an executable unit-test suite $U$, the structured runtime information $I$ needed to execute the repository (datasets and environment), and a Harbor-style reproducibility task bundle $B$. The naive approach is to ask an LLM to generate $C$ alone, as in prior repository-level code generation work \citep{seo2025papercoder}; but $C$ alone underspecifies reproducibility, because it conflates whether the code \emph{runs} with whether it computes the \emph{right} quantities. We therefore derive the evaluation artifacts $U$ and $I$ directly from $R$ rather than from $C$, so that the paper---not the generated code---remains the source of ground truth.

We classify every stage by the kind of mutation it performs on the repository:
\begin{description}[leftmargin=1em,itemsep=1pt,topsep=2pt]
  \item[\textbf{Create}] files that did not exist are written; repository \emph{structure} appears.
  \item[\textbf{Rewrite}] existing files are edited in place; \emph{behavior} changes while structure stays stable.
  \item[\textbf{Package/Spec}] the source is untouched; the stage emits a side artifact or wraps the repository.
\end{description}
A central observation of our analysis (Appendix~\ref{sec:appendix-casestudy}) is that the repository's \emph{structure} is established almost entirely by the early creation stages, whereas the later repair stage is overwhelmingly a \emph{content rewrite} over a stable set of files. We describe each stage below following the build path and the evaluation path of Figure~\ref{fig:workflow}.

\subsection{Plan}

\textbf{Objective.} Produce the blueprint that conditions all later code generation, without writing any source code.

\textbf{Mechanism.} The cleaned paper is read once and distilled into an overall reproduction plan, an architecture decision (the set of files that will exist and their responsibilities), a configuration template, and a per-file logic analysis. We prepend a preprocessing step that converts the input PDF into a cleaned JSON representation $R'$ (\texttt{paper.json}), with citation spans, bibliography entries, headers, and footers removed, so that every downstream stage reasons over the same canonical input. Crucially, every equation in the paper is extracted and recorded so that its literal presence can be checked after synthesis.

\textbf{Effect on the codebase.} None---this is a \textbf{Spec} stage. The repository is still empty; the outputs are planning side artifacts (plan, architecture, analyses, extracted equations) that become the authoritative context for synthesis. This stage and the analysis substep follow PaperCoder \citep{seo2025papercoder} closely; our contribution is the explicit extraction of equations and reported metrics, which later lets the rubric ground individual tests in specific paper quantities.

\subsection{Codebase}

\textbf{Objective.} Materialize the entire planned codebase as complete, runnable code.

\textbf{Mechanism.} Files are generated in dependency order, each conditioned on the plan, its own natural-language analysis, and the previously generated files. Every file in the planned task list is emitted as finished code rather than a \texttt{TODO} stub: the entry-point module, the per-component modules, a requirements file pinning package versions, and a configuration file. Paper equations are emitted \emph{literally}---coefficients appear as numeric constants rather than free parameters---and a bounded self-verification step may regenerate a file at most once if a required equation is found missing.

\textbf{Effect on the codebase.} \textbf{Create} at maximum scale: this is the moment the repository comes into existence, and it already contains essentially the full structural footprint that persists to the end of the pipeline. We refer the reader to \citet{seo2025papercoder} for full details of the planning, analysis, dependency-aware coding, and debugging substeps that this stage shares with PaperCoder.

\subsection{Codebase with Dataset Runner}

\textbf{Objective.} Make the synthesized code \emph{executable against real data and rival methods}.

\textbf{Mechanism.} First, an \textbf{evaluation plan} is produced: a catalog of the datasets and baseline methods the paper uses, each annotated with a feasibility decision (does it fit the hardware and storage budget?). Because faithfully running every baseline is rarely affordable, this stage deliberately \emph{selects a small, feasible baseline} as the comparison target (the \emph{Select Small Baseline} edge in Figure~\ref{fig:workflow}). Conditioned on that plan and on the rubric's dataset-loading information, the repository is then grown with the supporting machinery---data-preparation scripts, metric code, and dataset/baseline configuration files---and the real datasets and rival repositories are fetched into an assets area. A set of \textbf{baseline-runner modules} is added behind a single dispatch table, so any rival can be invoked through one entry point. This stage also absorbs runtime setup: a structured artifact $I$ records hardware requirements (e.g., GPU memory, CUDA version), package and Docker requirements, dataset endpoints and split specifications, training requirements, hyperparameters and seeds, and the metrics to be matched. Treating runtime setup as its own artifact---knowing that a paper needs CUDA~12 and a specific Torch version is not the same as knowing how to implement the model---lets us construct, verify, and reuse the environment independently of the code.

\textbf{Effect on the codebase.} \textbf{Create} of the runtime and evaluation layer: new infrastructure files and a baselines package. Behavior here is intentionally incomplete---the runners are first wired as \emph{stubs} that delegate to a bundled fallback and are smoke-tested, deferring faithful implementation to the repair stage.

\subsection{Iteratively-Fixed Codebase}

\textbf{Objective.} Bring the executable-but-incomplete code into faithful agreement with the paper.

\textbf{Mechanism.} The paper is first distilled into a \textbf{rubric}: a checklist of testable requirements broken into code-development, execution, and result-analysis items (``is this method actually implemented?'', ``is this exact hyperparameter present?''). Crucially, the rubric is conditioned on the paper and the structured plan artifacts, \emph{not} on the generated repository $C$ and \emph{not} on the grading harness. If the rubric were conditioned on $C$, the evaluation standard could be implicitly relaxed to fit whatever the coding agent happened to produce, and the paper would no longer serve as ground truth. The static repair loop then walks the rubric against the code and checks code-development items that can be judged without execution---that the loss function contains a required penalty term, that the configuration file uses the correct hyperparameter, or that a named module exists at the expected location. When an item fails, the LLM proposes minimal search--replace patches and the loop iterates, keeping a numbered backup of every file it touches.

\textbf{Effect on the codebase.} \textbf{Rewrite}, structurally stable. The file tree does not grow (modulo backups); the change is concentrated \emph{inside} existing files---for instance, rewriting a baseline stub into a faithful implementation, or aligning a configuration value to a paper-mandated constant. Many reproduction errors are visible in source code and are corrected cheaply here, before any training run is launched.

\subsection{Codebase in Docker}

\textbf{Objective.} Make the faithful codebase \emph{gradeable and portable}.

\textbf{Mechanism.} The rubric is operationalized into an executable \texttt{pytest} suite synthesized in two tiers.

\textbf{Intermediate-value tests.} These check algorithmic internals---loss terms, diffusion coefficients, normalization invariants, tensor shapes, or values derived from specific equations in the paper. They are the diagnostically richest part of the framework: a system can have the right final number for the wrong reason, but it is much harder to silently match a battery of intermediate quantities.

\textbf{Final-comparison tests.} These run benchmark-level checks: does the generated method match or outperform the selected baseline on the dataset and metric described in the paper? Final-comparison tests answer the externally visible question, while intermediate-value tests answer the internally faithful question. This division is the core methodological contribution of our framework: rather than asking ``does the final result look right?'', it asks ``did the implementation compute the important internal quantities correctly, \emph{and} did it also produce the right final result?''. Tests that reference a symbol the code does not actually expose are commented out and skipped rather than deleted, so a single hallucinated reference cannot break the whole run.

A planned \emph{runtime evaluation-and-fix} loop closes the pipeline: it reads $I$, builds the environment, downloads datasets and baselines, runs \texttt{reproduce.sh}, executes the \texttt{pytest} suite, reads \texttt{scores/scores.json}, feeds failing tests and logs back to the debugger, and patches and reruns until tests pass or an iteration cap is reached. The repository is then \textbf{packaged}, without source edits, into a self-contained container task: a \texttt{Dockerfile} baking in Python, \texttt{pytest}, and pinned dependencies; a task descriptor; a verifier entry script; and the repository plus its downloaded assets copied into the image.

\textbf{Effect on the codebase.} \textbf{Create} (the test suite) followed by \textbf{Package} (the source is frozen, not modified), yielding the portable Final Codebase. At the time of writing, the components of the runtime loop---dataset downloading, search--replace debugging, unit-test execution, and Harbor packaging---exist in isolation; the top-level orchestrator that sequences them autonomously is ongoing work.

\subsection{Recurring Design Principles}

Four invariants recur across stages and explain the observed behavior of the pipeline.
\begin{description}[leftmargin=1em,itemsep=1pt,topsep=2pt]
  \item[\textbf{P1: Equation-literal synthesis.}] Equations are emitted as code with constants inlined, and their presence is verified, making the synthesized code checkable against the paper rather than merely plausible.
  \item[\textbf{P2: Stub-then-implement baselines.}] Rivals are first wired as executable stubs behind a uniform interface, then faithfully implemented during repair. This separates \emph{integration} (does the runner dispatch?) from \emph{fidelity} (is the method correct?).
  \item[\textbf{P3: Grader-independent, rubric-driven repair.}] Repair is conditioned on the paper-derived rubric, not the grading harness, so fixes target genuine paper requirements and generalize instead of overfitting a held-out grader.
  \item[\textbf{P4: Non-destructive editing.}] Repairs rewrite in place with numbered backups, and hallucinated test references are skipped rather than deleted, so the pipeline never loses prior work---which is what keeps the file count stable through the repair stage (Appendix~\ref{sec:appendix-casestudy}).
\end{description}



\section{Experimental Setup}

We now describe the experimental setup and the metrics used to distinguish appearance-based from execution-grounded reproduction quality.

\textbf{Papers.} We evaluate the prototype on 22 papers drawn from PaperBench \citep{starace2025paperbench}, spanning a mix of deep-learning, optimization, and benchmark-style contributions. The papers were selected to cover a range of structural complexity and dataset requirements.

\textbf{Backbone.} The backbone model for all agents is GPT-5.2. Calls are routed through the same client and use a shared system-prompt template per stage; only the stage-specific instructions $\mathcal{T}_{\text{stage}}$ and the cleaned input $R'$ differ across calls.

\textbf{Environment.} Each generated repository is packaged into a Harbor-style task with paper JSON, generated code, runtime information, \texttt{pytest} tests, and a weighted reward script. Tasks are run under a 30-minute timeout on a local machine with an RTX 4060.

\textbf{Metrics.} We report three metrics that together separate
superficial faithfulness from execution-grounded reproduction:
(i) \emph{LLM Judge Score}, evaluated by GPT-5.2 against a set of
generated rubrics ;
(ii) \emph{Runnable Rate}, whether the repository can execute without
fatal errors; and
(iii) \emph{Reproduction Score}, a weighted score over code-development,
execution, and result-analysis tests; we do not separately report an
intermediate-value pass rate, since it is subsumed by this score.

\section{Results}

We report preliminary results on a 22-paper subset of PaperBench
together with BE-CBO, used as an in-depth case study. We treat
these numbers as a sanity check on the framework rather than as
a final evaluation; absolute values are likely to shift once the
runtime run-and-fix loop is completed and dataset and baseline
retrieval mature.
\subsection{Generated Repo Details}

To probe how closely generated repositories obey the paper that
produced them, we compared three Paper2Repro outputs against their
corresponding papers, rubrics, and official reference repositories:
BaM, APT (Adaptive Pruning and Tuning), and BBOX-ADAPTER. The
reference repositories are used as a behavioral calibration target,
not as a strict file-template oracle. Scores are rubric-weighted
implementation-faithfulness estimates, so they reflect both code
coverage and evidence that the paper's experiments were actually
reproduced. Table~\ref{tab:three_repo_summary} gives the headline
numbers, and the paragraphs below discuss each repository in turn.

\paragraph{BaM: Batch and Match.} The BaM repository is the strongest
of the three in terms of core mathematical logic. It implements BaM,
ADVI, Score-VI, Fisher-VI, and GSM-style algorithms with
full-covariance Gaussian variational families, synthetic target
distributions, per-iteration metrics, and shared experiment
infrastructure. This matches the paper's central claim that BaM is a
score-divergence-based black-box variational inference method with
closed-form Gaussian-family updates. Most paper-obedience gaps lie in
experimental detail rather than the algorithm skeleton: there is no
committed evidence of the required long seeded runs, grid-search
sweeps, final figures, or reproduced quantitative results. PosteriorDB
support is mostly generic scaffolding---target-specific log-posterior
and score functions for the paper's models are absent or replaced by
toy mechanisms---and the deep generative experiment is partial, with
CIFAR loading, VAE-style code, posterior scoring, and reconstruction
metrics in place but no trained decoder artifacts or completed
reconstruction outputs. BaM therefore obeys the paper at the level of
method structure, but not at the level of full experimental
reproduction.

\paragraph{APT: Adaptive Pruning and Tuning.} The APT repository
implements a plausible adaptive-pruning system. It contains an
APT-like adapter layer with frozen base weights, input/output masks,
dynamic rank expansion, salience-density pruning, rank allocation,
two-stage training, distillation scaffolding, evaluation utilities,
and RoBERTa/T5 configurations that encode many paper hyperparameters,
making the repository recognizable as an implementation of the
paper's high-level idea: adaptively tune salient parameters while
pruning unimportant structure to improve training and inference
efficiency. The main weaknesses are paper-critical details: baselines
are local proxies rather than the specified Mask Tuning and CoFiPruning
implementations, and several method details diverge from the paper or
reference behavior, including effective adapter scaling, multi-head
attention mask indexing, outlier salience, Equation-9-style adapter
salience, layer mapping for distillation, and KL prediction
distillation. The empirical side is especially weak: the only observed
run is a toy tiny-random RoBERTa SST-2 run with no pruning, while the
paper requires 60\% sparsity experiments, relative accuracy analysis,
efficiency claims, and ablations. APT therefore captures the broad
engineering direction of the paper, but does not obey it closely on
detailed mechanics or experimental evidence.

\paragraph{BBOX-ADAPTER.} The BBOX-ADAPTER repository contains a
substantial adaptation pipeline: scalar question--answer pair scoring,
ranking/NCE-style adapter training, online positive/negative example
storage, single-step reranking, sentence-level full-step beam search,
dataset preparation, and metric utilities. It also recognizes several
important paper settings from Appendix~H.2, including maximum
generation length 512, temperature 1.0, learning rate $5\!\times\!10^{-6}$,
batch size 64, 6000 training steps, AdamW, and beam size 3. Dataset
manifests show materialized GSM8K, StrategyQA, TruthfulQA, and
text-only ScienceQA splits. The repository nonetheless falls short of
paper-faithful reproduction: there are no committed adapter
checkpoints, training logs, evaluation summaries, or reproduced
numbers for the paper's main tables; the default configuration is not
runnable as-is because config keys expected by the loader do not match
the provided YAML; the ranking loss path has an indentation bug
affecting \texttt{RankingNCELoss.forward}; and the Equation~3 score
regularizer is effectively disabled by default because the
$\alpha$ value is not resolved from the expected configuration
location. Several paper components---MLM ablation, fine-tuning
baselines, plug-and-play results, cost trends, and the Mixtral
white-box extension---are stubs or planned aggregations rather than
completed experiments.

\paragraph{Cross-paper interpretation.} Across all three repositories,
the dominant pattern is the same: generated code often captures the
high-level method and implements plausible scaffolding, but falls
short on paper-specific detail and experimental proof. BaM is most
convincing on core algorithmic logic; APT is most coherent as an
engineering framework for pruning and tuning, yet shows the largest
gap between method scaffold and paper-scale results; BBOX-ADAPTER
has the broadest pipeline for a black-box LLM adaptation workflow,
but suffers from configuration and loss-path issues that make
reproducibility fragile. These comparisons argue that generated
repositories should be treated as starting points for reproduction
rather than as faithful reproductions of the papers themselves:
useful for studying how much of a method an automated coding system
can reconstruct, but requiring substantial human correction before
they can support paper-level empirical claims.

\subsection{Paper2Code vs.\ Paper2Repro}

baseline-outperformance is sensitive to factors outside the

amelioration loop is not designed to fix and that the runtime
run-and-fix loop is intended to address.

Figure~\ref{fig:pipeline_scores} tracks the reproduction score as a
repository walks the build path of Figure~\ref{fig:workflow}, from the
Paper2Code baseline through synthesis (\textbf{Codebase}), static
repair (\textbf{Iteratively-Fixed Codebase}), and baseline wiring
(\textbf{Codebase with Dataset Runner}). The headline is that every
stage clears the Paper2Code baseline, but the climb is not steady: the
score can \emph{fall} after the Iteratively-Fixed Codebase stage and
after the Codebase with Dataset Runner stage rather than rising at
every step.

Two mechanisms explain these dips. \emph{First, real regressions.}
Both repair and baseline-wiring are search--replace edits over code
that already runs, so satisfying one rubric item can break another
that previously passed. The repair stage, for example, reliably broke
\emph{all-in-one}'s Hodgkin--Huxley noisy-time-series summary
statistic---a leaf that passed right after synthesis and failed once
repair had touched the surrounding file. The baseline-wiring stage is
even clearer: in \emph{bridging-data-gaps} it reliably broke the
\textbf{adaptor module} and the \textbf{CDC} baseline---the very rival
methods it is meant to wire in---and in \emph{stochastic-interpolants}
it broke the in-painting time-derivative interpolant. Because each
edit is local but the rubric is global, a stage can add the feature it
targets and silently disturb a neighbor. \emph{Second, a
nondeterministic grader.} The judge scores each rubric leaf by first
asking an LLM to pick the relevant files from the repository, then
reading only those and scoring $0/1$ with an instruction to ``treat
missing as failure.'' That file-selection step varies run to run, so a
leaf can flip $0\leftrightarrow1$ on \emph{identical} code. A
single-run bar therefore mixes genuine movement with this flicker,
which is why the cross-stage analysis trusts how many of three runs a
leaf passes rather than any one run.

Read through the multi-run signal, the net picture is steadier than
the single-run bars suggest. The Iteratively-Fixed Codebase stage is
the consistent within-tool win: it contributes reliable
($3\text{/}3$) gains in all three papers---for instance
\texttt{random\_fourier\_features=False} in
\emph{stochastic-interpolants}, the gradient-of-output-layer and
$10$-shot generation code in \emph{bridging-data-gaps}, and the
provided training loop plus the Webb-2018 edge-update algorithm in
\emph{all-in-one}. The Codebase with Dataset Runner stage is
paper-dependent: it helps \emph{stochastic-interpolants} but
net-regresses \emph{bridging-data-gaps}, precisely because it breaks
the adaptor and CDC baselines it is supposed to add. The practical
takeaway is to trust the multi-run stability of a stage rather than an
isolated single-run dip.

\subsection{Replication Results of the Final Repo}

The scores reported above are rubric-weighted, LLM-graded estimates of
\emph{implementation faithfulness}; they do not by themselves show a
generated repository \emph{executing} on real model weights. As a
preliminary check that the final artifact actually runs, we executed one
generated repository end-to-end---\emph{bridging-data-gaps} (DPMs-ANT)---
rather than only scoring it, giving a concrete instance of the runtime
loop the rest of this paper treats as future work. The run used an RTX
4060 (8\,GB), loading the real pretrained DDPM
\texttt{google/ddpm-ema-celebahq-256} (an FFHQ-like face source standing
in for the paper's source domain) and a real $10$-image target
(\texttt{huggan/anime-faces}, the closest public stand-in for the paper's
curated $10$-shot sets, which are not downloadable). We stress at the
outset that these are \textbf{real numbers on real weights, but they are
not the paper's numbers}: they answer ``does the adaptation pipeline run
on real weights?'' (yes), not ``does it match the paper's tables?''.

\textbf{What moved.} On the $10$ target images, training loss dropped
$0.0177 \rightarrow 0.0080$, and the held-out $\epsilon$-MSE improved
$0.00968 \rightarrow 0.00876$ ($\sim$9.5\%; Table~\ref{tab:bridging_repro}),
i.e.\ the model genuinely shifted toward the target domain. The repo's own
Intra-LPIPS metric produced a real number ($0.5101$, over $12$ generated
samples at $50$ DDIM steps), and the whole run took $86$\,s at a peak of
$6.43$\,GB VRAM. The held-out gain is modest \emph{by design}: only $60$
adaptation steps, only $56$\,K norm-only parameters, and an evaluation
averaged over all noise levels (high-noise timesteps are nearly
domain-independent and dilute the signal). The training-loss drop is the
clearer evidence that real adaptation is happening.

\textbf{What this run does and does not show.} This is a deliberately
reduced-scale demonstration, and several gaps separate it from the paper's
reported results. The target domain is anime faces rather than the paper's
curated sunglasses/babies/sketches; we run $60$ steps rather than $300$;
we adapt by norm-tuning rather than with the ANT adaptor; there is no
classifier or adversarial-noise stage; and Intra-LPIPS is computed over
$12$ samples rather than $1000$. The ANT method proper was \emph{not} run:
its \texttt{train\_classifier}~$\rightarrow$~\texttt{train\_ant}~$\rightarrow$~\texttt{eval}
pipeline enforces batch~$40$ / $300$ iterations / $1000$-sample
evaluation and needs source images plus a classifier checkpoint, but
batch-$40$ at $256$\,px does not fit $8$\,GB and a $1000$-sample
evaluation takes hours. We also hit a genuine codebase bug: the repo's own
\texttt{AdapterInjector} mis-wires modules on a real \texttt{diffusers}
UNet (a $512$-channel bottleneck block ends up executing at a
$128$-channel/$256$\,px position, raising a \texttt{GroupNorm} channel
mismatch), so to stay within budget we disabled the broken adapter and
adapted via norm-tuning while still reusing the repo's real
\texttt{DiffusionModelWrapper.predict\_eps}, \texttt{NoiseSchedule}, and
Intra-LPIPS core. What the run \emph{does} establish is concrete: real
pretrained weights load through the repository's wrapper, the real
forward-noising~$\rightarrow$~$\epsilon$-prediction~$\rightarrow$~adaptation
loop runs end-to-end on real data within $8$\,GB, the loss moves the right
way, and the repository's metric yields a real number---the gap to
matching the paper's tables is one of compute budget and access to the
paper's data, not of a pipeline that fails to run.

\section{Discussion}

\paragraph{Answering RQ1.} The gap between LLM judge scores and
intermediate-value pass rates supports the claim that
``seems good'' is not enough. A judge that inspects only the
final repository can miss a missing penalty term, an off-by-one
normalization, or an incorrect optimizer setting that does not
prevent the code from running.

\paragraph{Answering RQ2.} Intermediate-value tests are the
strongest diagnostic component of the framework. In several
case studies, an intermediate-value test caught an error that
neither LLM judge inspection nor final metric comparison could
isolate, because the final metric was either similar to baseline
by coincidence or unreachable due to a separate runtime issue.

\paragraph{Answering RQ3.} The static amelioration loop already
provides substantial improvements in code-development quality at
low cost. The full answer to RQ3, however, requires the
completed runtime run-and-fix loop, which we leave to future
work.



\section*{Limitations}

This work has several limitations. First, the runtime run-and-fix
loop is not fully implemented; while the components exist, the
top-level orchestrator that ties them into a single autonomous
process is future work. Second, our experiments cover 22 papers
under a single backbone (GPT-5.2) and a single hardware budget;
broader coverage and multiple-seed runs are needed before any
conclusions about absolute performance can be drawn. Third, our
intermediate-value tests are themselves LLM-generated from the
paper; while we keep them blind to the generated repository,
they may still inherit biases from the backbone, and a careful
audit of test quality is needed. Fourth, dataset and baseline
fetching are not always reliable, and some failures are
infrastructure failures rather than implementation failures.
Fifth, we do not yet run formal ablations isolating the
contribution of each stage.

\section{Future Work}

\textbf{Full runtime orchestrator.} The most immediate next step
is to implement the full runtime run-and-fix orchestrator that
sequences environment build, dataset retrieval,
\texttt{reproduce.sh} execution, test running, log ingestion, and
patch application into a single loop bounded by an iteration
cap.

\textbf{Stronger environment builder.} Many papers require
specific CUDA versions, Torch versions, GPU memory budgets, or
non-Python dependencies. A better environment builder should
translate the runtime-info JSON into a concrete \texttt{Dockerfile}
and installation script, with verifiable post-build checks.

\textbf{Improved dataset and baseline fetching.} Preliminary
results suggest that low reproduction scores are often caused by
dataset retrieval or baseline availability, not by model
implementation errors. Targeted improvements in this area are
likely to raise reproduction scores more than additional
amelioration of model code.

\textbf{Formal ablations.} Important ablations include removing
intermediate-value tests, removing static amelioration, removing
runtime feedback, and comparing against a PaperRepro-only
baseline under matched conditions. These ablations would
quantify the contribution of each component of the framework.

\textbf{Stronger case studies.} BE-CBO illustrates how
intermediate-value tests detect whether key algorithmic
components are correctly implemented. Negative cases are equally
informative, since they show how repositories may be runnable
yet scientifically incorrect, and they argue most strongly for
execution-grounded evaluation.

\section{Conclusion}

PaperRepro asks whether an LLM can generate a faithful-looking
repository from a paper. Terminal-Bench asks whether an agent can
solve realistic terminal tasks under tests. Our project sits
between the two and asks whether a paper-to-code system can
generate a repository that not only looks good, but also runs
and satisfies paper-specific scientific reproduction tests. We
present a rubric- and execution-guided framework that turns a
paper into an initial repository, paper-specific rubrics,
intermediate-value tests, runtime requirements, and a Harbor-style
reproducibility task. On 22 PaperBench papers, the prototype
substantially improves runnability and exposes a large gap between
executable and scientifically reproducible repositories. We view
this as evidence that paper-to-code evaluation should move beyond
LLM-as-a-judge scores toward execution-grounded verification of
algorithmic and experimental fidelity.
